# Mind Protocol 0.9.0

Mind Protocol `0.9.0` is the first formal GitHub Release and the compatibility-freeze milestone immediately before `1.0.0`.

## Highlights

- freezes manifest schema `v3` as the pre-1.0 root shape;
- removes redundant `mind.kind` in favor of `mind.subject.type`;
- removes GitHub/provider-specific `public_organizations` from the core manifest;
- adds a machine-readable compatibility policy;
- fingerprints every published JSON Schema to prevent silent in-place contract drift;
- keeps reusable schema bytes release-agnostic when the same `$id` is intended to survive the `0.9` → `1.0` release train;
- enforces exact protocol version, lifecycle state, and migration-source binding semantically;
- defines `module` as the capability-negotiation unit;
- defines unknown optional/required/default-loaded module behavior;
- rejects unknown root-manifest fields;
- defines the initial `1.x` compatibility rule;
- defines supported stable migration floor `0.6.0`;
- adds deterministic manifest v2 → v3 migration;
- keeps canonical provider-independent Identity, relationships/provenance, visual identity, agent identity, neutral baseline, and dual-mode conformance semantics intact.

## Compatibility freeze

The release publishes `compatibility.yaml`, which records:

- frozen manifest schema version;
- removed pre-1.0 aliases;
- exact `$id` and content fingerprint for every published schema;
- forward-compatible extension policy;
- supported migration floor and stable source lines;
- prohibition on inferring canonical entity IDs from provider logins.

The freeze is deliberately strict: compatible extension happens through optional modules or versioned optional resources, not arbitrary new root fields.

A schema `$id` identifies one schema shape, not one protocol release number. Release-specific values are checked by semantic validators so advancing to `1.0.0-rc.1` or `1.0.0` does not require mutating otherwise unchanged schema bytes under the same published identity.

## Conformance

The public conformance suite targets `[0.9.0, 1.0.0)` and covers synthetic:

- person;
- organization;
- agent;
- project;
- product.

Both `schema` and `minimal` consumer modes must agree on deterministic outcomes for:

- authored-vs-derived relationship provenance;
- canonical visual resolution;
- canonical visual integrity failure;
- unknown optional modules;
- unknown required/default-loaded modules;
- removed manifest aliases;
- unknown root-manifest fields.

## Migration

Direct supported stable migration sources begin at `0.6.0` and include `0.6.0`, `0.7.0`, and `0.8.0` for this release.

See [`../MIGRATION_0.9.md`](../MIGRATION_0.9.md).

The manifest v2 → v3 migration:

- checks `mind.kind` against `mind.subject.type` before removal;
- removes provider organization projections only after their intended meaning is preserved elsewhere;
- never infers canonical organization IDs from provider logins;
- preserves `mind.context_version` unless concrete durable context independently changed.

## Neutral baseline

The release baseline is generated deterministically from the exact release commit and includes:

- `protocol.yaml`;
- `conformance.yaml`;
- `compatibility.yaml`;
- abstract manifest schema v3;
- all published schemas;
- deterministic digest inventory.

## Publication sequence

`0.9.0` is the first formal GitHub Release.

Next formal publications:

- `1.0.0-rc.1` — GitHub prerelease;
- `1.0.0` — first compatibility-guaranteed stable release.

After the exact `v0.9.0` artifact is published, a deliberately small set of existing concrete minds may synchronize to it as compatibility canaries before the RC. Canary synchronization is evidence about the released contract; those repositories do not become protocol authority and must not add named/provider-specific requirements to the core.

The full named identity, visual-family, provider-binding, agent, project/product, and broader ecosystem rollout begins only after stable `1.0.0`.
