# Mind Protocol 1.0.0-rc.1

Mind Protocol `1.0.0-rc.1` is the final-contract release candidate built from the public `0.9.0` compatibility freeze.

It is a **GitHub prerelease**, not yet the `1.x` compatibility guarantee. That guarantee begins only when stable `1.0.0` is published.

## Exact delta from 0.9.0

The candidate deliberately keeps the frozen protocol surface intact. The reviewed changes from `0.9.0` are limited to release identity and machinery required to represent the RC correctly:

- protocol version advances from `0.9.0` to `1.0.0-rc.1`;
- compatibility lifecycle advances from `frozen_pre_1_0` to `release_candidate`;
- conformance support range becomes `>=1.0.0-rc.1 <1.0.0`;
- supported stable migration sources now include the formal `0.9.0` line in addition to `0.6.0`, `0.7.0`, and `0.8.0`;
- protocol validators use strict SemVer 2.0 prerelease precedence rather than comparing only major/minor/patch;
- numeric prerelease identifiers with illegal leading zeroes are rejected semantically;
- build metadata is ignored for precedence as required by SemVer 2.0.

No published JSON Schema shape changes in this candidate. The `0.9.0` frozen schema `$id` values and Git blob fingerprints therefore remain unchanged.

No named person, organization, agent, project, product, provider, renderer, or repository layout becomes a universal protocol dependency.

## Conformance

Both required consumer modes continue to exercise the five synthetic subject types:

- person;
- organization;
- agent;
- project;
- product.

The RC specifically proves that `1.0.0-rc.1` is inside the half-open range `[1.0.0-rc.1, 1.0.0)` while stable `1.0.0` is outside that candidate-only range.

Regression coverage also proves:

- `1.0.0-rc.1 < 1.0.0`;
- `1.0.0-rc.2 > 1.0.0-rc.1`;
- build metadata does not alter precedence;
- invalid numeric prerelease identifiers are rejected.

The existing provenance, canonical visual resolution/failure, unknown optional/required module, frozen root-manifest, neutral baseline, and dual-consumer probes remain required.

## Migration from 0.9.0

A conforming `0.9.0` Mind does not need a manifest-shape migration to consume this RC. Manifest schema remains `v3`, and the frozen resource schemas are unchanged.

A concrete consumer should:

1. pin the exact published `v1.0.0-rc.1` contract artifact after publication;
2. update its declared protocol version to `1.0.0-rc.1`;
3. keep its independent `mind.context_version` unchanged unless durable authored context also changes;
4. rerun its normal Mind contract validation against the exact RC contract set.

See [`../MIGRATION_1.0.md`](../MIGRATION_1.0.md).

## Known limitations

- `1.0.0-rc.1` carries no stable `1.x` compatibility promise yet;
- full named visual-family, provider-binding, agent, project/product, and ecosystem rollout remains post-`1.0.0` work;
- a blocking universal semantic defect discovered after publication requires a later RC (`rc.2` or later), never mutation of the `rc.1` tag;
- concrete implementation defects remain owned by the affected implementation and do not automatically imply a protocol revision.

## Publication boundary

Merging this source candidate does not publish it. Formal publication is a separate manual action through `Publish Mind Protocol Release`, using prerelease channel, after the merge tree is proven identical to the green PR-head tree.

The immutable publication target, if approved, is `v1.0.0-rc.1`.
